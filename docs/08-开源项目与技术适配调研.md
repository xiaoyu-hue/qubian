## 1. 大白话结论

找到了一批能直接用的开源项目，但真正值得复用的只有三类，其余要么跟现有架构打架，要么许可证有坑。

**三类值得复用**：一是浏览器内跑 Python 判题的成熟做法（有人已经把 Pyodide 封装好，架构跟我们几乎一模一样）；二是题库"生成—校验—打回重做"的自动流水线（Meta 开源的框架就是我们规范里那套自愈循环的原型）；三是免费编程书单的权威数据源（40 万星、许可干净，正好做外部书籍导航）。

**三类不建议引入**：游戏化库（会把已经写好的纯函数逻辑拆散，破坏分层）、成套液态玻璃组件库（跟"自研为主 + 克制点缀"的既定决策冲突）、需要后端的服务（跟"暂不做后端"冲突）。

还有一个意外收获：好几个明星项目的底层选型（React 19 + TypeScript + Vite + Tailwind 4 + CodeMirror 6 + Pyodide）跟趣编一模一样。这说明当初的技术选型没走弯路，也意味着这些项目的架构可以直接对照抄作业。

## 3. 逐项分析

### 3.1 实操题自动判题（T2.1 / T2.2）

**找到什么**

- **py-runner**（andrewjamesmoore/py-runner，MIT）：React + TypeScript + CodeMirror 6 + Pyodide + Vite。跟趣编技术栈逐项对齐。关键做法：Pyodide 跑在 Web Worker 里（不卡界面）、执行超时限制、限制可导入模块、禁文件系统、stdout/stderr 从 worker 管道传回。
- **ipy.me**（Ansen/ipy.me，MIT）：纯前端 Python 练习站，Pyodide + CodeMirror 6，深浅色自动跟随系统并支持手动切换，移动端响应式，首次加载约 10MB WASM。
- **judge-beginner**（OrangeAppleTW，原仓库已停更迁至 OrangeApple-Lab）：纯前端判题，按预设测试用例自动评分；题目数据拆成 `problems.json` 索引 + 每题一个 JSON，还配了一份"出题指南"。这个数据组织方式跟我们 05 规范的分文件方案几乎一致。
- **apcs-judge**（Yu-0312）：Pyodide + Judge0 CE 双运行时，纯静态站点无自建后端；有 `check-data.js` 数据校验并接入 CI、错題本、localStorage 学习状态 + 快照回滚。这套"数据校验 + CI"正是我们 T1.4 / T2.4 想做的事。
- **Judge0 CE**：服务端沙箱，支持 13–60 种语言，但**必须有后端**，只适合放到阶段 3 的多语言评估（T3.3）。

**坑在哪**

- Pyodide 首次加载约 10MB，弱网和手机端要显示加载态，否则用户以为卡死（我们 T0.10 的骨架屏正好派上用场）。
- 浏览器内执行没有真正的安全隔离强度保证，py-runner 靠"限制导入 + 超时 + 无文件系统"降低风险，可以照搬这套约束。
- judge-beginner 已停更，不要直接依赖，只借鉴思路。

**建议**

以 `src/lib/pyodide.ts` 自己封装，把 py-runner 的 Worker 架构和约束清单作为实现清单；测试用例的执行方式参考 judge-beginner。`gradeCode` 接口保持不变，符合实施计划 4.3 的"换实现不动上层"。

### 3.2 题库自动生成 + 自愈校验（T2.3–T2.5）

**找到什么**

- **synth_gen**（Meta / facebookresearch，MIT，已核实）：这是最重要的发现。它的核心机制是"生成 → 校验器检查 → 失败就报错 → 让模型自己改 → 循环到通过"，校验器分三层：PythonSyntaxVerifier（语法）、MypyVerifier（类型）、PythonTestBasedVerifier（跑测试）。另有 seed source 提供多样化种子，避免生成题目千篇一律。**我们 05 规范第 9 节的自愈循环，本质上就是这套框架的缩小版**——这验证了规范方向是对的。
- **KodCode**（KodCode-AI，代码 Apache-2.0，但数据声明 CC BY-NC 4.0）：12 个子集的大规模合成题库，Self-Verification + pytest 并行执行。**许可证有坑**：代码和数据许可不一致，README 明确写"Please follow CC BY-NC 4.0"，NC 会限制他人商用改编，跟我们"开源 + 允许改编"的定位有冲突。
- **InfoSynth**（ishirgarg，学术项目，许可证未核实）：遗传算法 + 迭代反馈生成题目，宣称 97% 准确率，可控难度与多样性，但需要 API Key，偏研究用途。
- **exercise-10k**（ASSERT-KTH，许可证未核实）：1 万道 AI 生成 Python 题，JSON 结构（id/title/description/difficulty/topics/sample_input/output + answers）可参考。但公开统计里只有 71.69% 的解法能成功执行——质量参差，不能整批入库。
- **Djinn**（EleutherAI）：生成"预期解法 + 故意漏洞"的题目用于安全验证，偏安全研究，跟趣编关系不大。

**坑在哪**

- 这些框架都要调大模型，属于**离线工具链**，在开发者电脑跑，不进前端——这一点跟我们"暂不做后端"不冲突，但会产生 API 成本。
- CC BY-NC 类数据不能进我们的 Apache-2.0 题库，即使我们自己非商用，也会限制下游改编者。

**建议**

T2.3–T2.5 按 synth_gen 的三层校验器模型设计脚本：结构校验（JSON Schema）→ 参考实现跑测试 → 注入烂代码防弱测试。这套我们已经写在 05 规范里，不用改方向；接入时把"模型自修正"这一步做成可选（有 API Key 才启用），没 Key 时用规则生成 + 人工抽查兜底。KodCode 的数据只作结构参考，不导入正文。

### 3.3 代码编辑器（T1.8）

**找到什么**

对比 CodeMirror 6 与 Monaco，两份独立评测结论一致：

| 维度 | CodeMirror 6 | Monaco（VS Code 内核） |
|---|---|---|
| 体积 | 核心约 300KB，模块化按需加载 | 约 1–2MB（gzip 后），worker 配置复杂 |
| 移动端 | 一流触摸与虚拟键盘支持 | 基本不支持移动端 |
| 无障碍 | 内置，读屏与键盘导航良好 | 良好但配置更重 |
| 语言服务 | 插件式 IntelliSense | 内置完整 IntelliSense |
| 代表性项目 | Sourcegraph、Replit 均从 Monaco 迁至 CodeMirror | 桌面 IDE 场景 |

**建议**

维持 T1.8 原计划选 CodeMirror 6。趣编是移动端优先、只需要 Python 语法高亮，CodeMirror 的体积和移动端优势正好命中；Monaco 的重型语言服务在这里用不上，还会拖慢首屏。py-runner、ipy.me、coding-drills 都用 CodeMirror 6，可直接参考接法。

### 3.4 游戏化（T1.10–T1.14、T2.6–T2.8）

**找到什么**

- **Questro**（npm，MIT，已核实）：12 个模块的 React 游戏化库，覆盖 Points / Badges / Quests / Leaderboard / Levels-XP / Streaks / Notifications，还有 Combo Meter、Daily Challenge、成就弹窗、进度环等视觉组件。零依赖（除 React）、TypeScript、unstyled（不自带样式）。功能清单跟趣编需求几乎逐项对应。
- **Trophy UI**（trophyso/ui，MIT）：17 个游戏化 UI 组件，按 shadcn registry 分发——代码直接复制进项目，归你所有，不受上游版本约束。适合当视觉参考。
- **Gami.Fied**：服务端 AGPL-3.0（SDK/UI 是 MIT），要 Docker + Postgres + Redis，**跟"暂不做后端"直接冲突**，且 AGPL 传染性强。不推荐。
- **react-achievements**：非商用 MIT、商用付费的双许可。趣编非商用可用，但许可分层要留意。

**坑在哪（关键）**

趣编已经在 `src/domain/` 里用纯函数实现了 economy / tasks / progression，还配了单测；`scripts/check-boundaries.mjs` 明确禁止 domain 层依赖 React。引入 Questro 会把游戏化逻辑从纯 domain 层拽进 React Provider，**直接破坏我们最看重的可测试分层**。而且 Questro 的成就弹窗带 confetti 满屏庆祝，跟 D3"克制点缀"决策冲突。

**建议**

不引入游戏化库代码。保留自研纯函数；只把 Questro 的 12 模块清单当作二期功能 coverage 的对照表，把 Trophy UI 的 Streak Calendar / Progress Ring 当视觉参考。这样既不破坏架构，也不增加依赖。

### 3.5 书城外部导航数据源（T1.17）

**找到什么**

- **EbookFoundation/free-programming-books**：约 40 万星的免费编程书/教程/课程索引，覆盖 30+ 语言和多个主题，Markdown 列表，有官方搜索站。多数资料指向 CC BY 4.0（个别资料说 MIT，**以仓库 LICENSE 为准，接入前核实**）。
- **justjavac/free-programming-books-zh_CN**：中文版，约 11.7 万星，适合中文读者。

**坑在哪**

它是**链接索引，不是书籍正文**。这正好符合 PRD F09"外部免费书籍导航"的定位，也符合 05 规范"CC BY 可用但需署名、不内嵌 SA/NC 正文"的合规红线。风险点在于：条目质量靠社区维护，链接可能失效，做导航前要人工抽查。

**建议**

T1.17 用它做数据源，卡片标注来源与许可、只跳转原站不内嵌正文，按 CC BY 要求署名。首批只放少量已核实条目（实施计划 2.3 默认值），不做全量导入。

### 3.6 液态玻璃视觉（T0.3，已完成）

**找到什么**

- **glass-refraction**（Z1Code，MIT，已核实）：CSS + React，SVG 折射滤镜 + 高光 + 色散，CSS 变量可主题化，浏览器支持明确。
- **liquid-glass-component-library**（ObaidQatan，实验性、不接受贡献）：70+ 组件，React 19 + TS 5.9 + Vite 7 + Tailwind 4.1，跟趣编栈几乎逐项一致。

**建议**

T0.3 已完成，自研玻璃卡片符合 04 规范参数。这些库只作为"效果想升级时"的参考，不引入：一是 D1 已定"自研为主"，二是成套组件库会带来依赖膨胀和 AI 味，三是它的满屏折射效果跟 04 规范反模式清单冲突。

## 4. 三视角分析（三个关键决策）

用户约定的决策方法：先全力反驳，再切换到支持方，最后中立对比。

### 决策一：判题是自己封装 Pyodide，还是直接引入现成项目？

- **全力反驳**：自己封装重复造轮子，py-runner 已经把 Worker 隔离、超时、模块限制全做好了，直接拿来改最快、最稳。
- **切换支持**：现成项目是完整 App，交互和数据模型跟趣编的题目结构、双答案、金币结算对不上；整段搬进来会产生大量胶水代码，反而更难维护。自己封装只需一个 `pyodide.ts`，接口还能保持稳定。
- **中立对比**：两者的真实差异是"复用运行层" vs "复用整App"。运行层复用价值高、成本低；整 App 复用价值低、改造成本高。
- **建议**：封装自己的运行层，借鉴 py-runner 的实现清单。这项不需要用户额外拍板，符合原计划。

### 决策二：游戏化逻辑要不要换成 Questro？

- **全力反驳**：Questro 12 模块全覆盖、零依赖、MIT，省掉我们自己写积分/等级/成就/打卡的时间，功能还更全。
- **切换支持**：它把逻辑绑在 React Provider 上，而我们 domain 层是纯函数 + 单测 + 分层约束脚本保护。引入等于拆掉我们的架构基线，后续测试和替换成本更高；视觉庆祝还跟 D3 冲突。
- **中立对比**：省短期编码 vs 保长期可维护性。我们的题库、判题、经济都是纯函数驱动，一致性比省几天编码更重要。
- **建议**：不引入。这项需要用户确认——如果坚持"能用现成就用现成"，就必须同时接受 domain 分层被打破，属于架构级变更。

### 决策三：题库数据用 KodCode 这类现成数据集，还是继续自生成？

- **全力反驳**：现成几十万道题，直接筛选入库，比 AI 一道道生成快得多。
- **切换支持**：KodCode 数据 CC BY-NC 4.0 会限制下游改编；exercise-10k 只有 71.69% 解法可执行；而且这些题都没有趣编的"专业版 + 大白话版"双答案，入库还得逐题补写，省力有限。
- **中立对比**：现成数据的量很大，但和我们格式契合度低、许可有附加条件；自生成慢，但格式、双答案、版权完全可控。
- **建议**：继续自生成，现成数据集只作结构参考。这项符合 05 规范既定红线，不需要额外拍板。

## 5. 原创与复用的边界

| 层面 | 该原创 | 该复用 |
|---|---|---|
| 产品差异化 | 双答案（专业版/大白话）、金币经济数值、任务强度、关卡解锁 | — |
| 领域逻辑 | 判分、经济、进度、任务的纯函数与单测 | 功能清单（Questro 12 模块）作为对照 |
| 运行层 | `pyodide.ts` 封装（适配我们的题目结构） | Worker 隔离 + 超时 + 模块限制的实现清单 |
| 工具链 | 离线生成脚本 + 三层校验 + 自愈循环 | synth_gen 的 verifier 模型与 seed 机制 |
| 数据与内容 | 题库正文、小册子汇编 | 免费书单的链接索引（署名、不内嵌） |
| 视觉与交互 | 玻璃样式、三端布局、状态组件 | 效果参考（glass-refraction、Trophy UI） |

一句话：**面向用户的功能体验和领域逻辑必须原创，通用的运行层、工具链方法和外部书单可以复用。**
