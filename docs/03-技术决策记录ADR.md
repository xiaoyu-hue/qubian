## 0. 什么是 ADR（大白话）

ADR 就是给每个重要技术选择写一张"决策卡片"：**当时面临什么问题、有哪些选项、最后选了哪个、为什么、有什么代价**。这样几个月后回头看，就知道当初的 rationale（理由），而不是只剩一个结论。

本文件采用经典格式：**背景 → 备选方案 → 决定 → 理由 → 后果（正面/负面）**。

## 2. 决策详情

### ADR-001：产品双目标——既学会编程，又做成产品

- **背景**：项目初衷是"通过做应用来学编程"，同时把它当正式产品面向他人。
- **备选方案**：
  - A. 只学编程：做几个小工具练手，不做完整产品；
  - B. 只做产品：专注产品交付，编程是副产品；
  - C. 双目标并行。
- **决定**：C，双目标并行，以真实需求驱动。
- **理由**："双版本答案"这个设计恰好把两个目标缝在一起——为了把知识讲给零基础的自己听，必须真正理解；而做产品逼着把知识讲清楚，正是学会的标志。需求来自真实痛点。
- **后果**：
  - ✅ 需求真实、有持续动力；
  - ⚠️ 时间主要花在做产品上，学到的偏"用 AI 拼应用"而非"从零手写代码"——该取舍已明确。

### ADR-002：题目形态——选择题 + 实操题 + 双版本答案

- **背景**：题目要求"带答案"，需要确定题型和答案形式。
- **备选方案**：
  - A. 只做选择题（易测概念，自动判分）；
  - B. 只做实操题（练写代码，判分难）；
  - C. 两种都要 + 每题双版本答案。
- **决定**：C。
- **理由**：选择题解决"懂不懂概念"，实操题解决"会不会写代码"——只看懂答案写不出代码是学编程失败的常见陷阱。双版本答案（专业版给有基础者、大白话版给零基础）是差异化卖点。
- **后果**：
  - ✅ 覆盖理解与动手，两类用户各取所需；
  - ⚠️ 实操题判分难，需分阶段解决（见 ADR-005）。

### ADR-003：教学语言——Python 先行，Rust 暂缓

- **背景**：需明确 Rust / Python 的引入范围，区分"教什么"和"用什么开发"。
- **备选方案**：Python 先行 / 加 Rust / 加 JS。
- **决定**：第一批只教 Python；Rust 进远期备选；将来第二语言优先考虑 JavaScript。
- **理由**：Python 对零基础最友好；Pyodide 已支持浏览器内跑 Python 判题；MIT 中文题库（bosens-China）也是 Python。Rust 有所有权/借用检查器等概念，零基础会被劝退，浏览器运行还要转 WebAssembly，链路复杂。
- **后果**：
  - ✅ 起步最顺、判题现成；
  - ⚠️ 语言单一，靠 ADR-014 的扩展点设计留门。

### ADR-004：开发语言——TypeScript + React，放弃 PyQuest 单文件

- **背景**：早期调研推荐 PyQuest（单文件 JS）作基座；最终改用完整 React 技术栈。
- **备选方案**：
  - A. PyQuest 单文件原生 JS（最简单，最快验证）；
  - B. bosens-China（TS + React 工程化，中文内容现成）；
  - C. 从零搭 React + TypeScript 工程。
- **决定**：C，React + TypeScript + Vite + Tailwind + shadcn/ui，从零搭。
- **理由**：产品定位为"当产品做、面向他人、开源、可持续维护"，界面状态多（金币/关卡/判题/成就），框架的自动状态管理能省大量 bug；React 是行业最主流、AI 写得最稳、开源/招人友好。该决定意味着放弃 PyQuest 单文件路线。
- **后果**：
  - ✅ 长期可维护、AI 好写、生态成熟；
  - ⚠️ 概念多、配置多，起步比单文件慢——靠分阶段交付与文档化缓解。

### ADR-005：判题方案——分三档，不一步到位

- **背景**：实操题自动判分技术难度最高，需控制复杂度。
- **备选方案**：
  - A. 自评式（对照答案点"我懂了"）；
  - B. Pyodide 浏览器内跑 Python 判题；
  - C. judge0 沙箱服务（多语言，需 Docker 部署）。
- **决定**：分三档递进——MVP 用 A（自评），二期用 B（Pyodide），远期视需求用 C（judge0）。
- **理由**：A 几天能跑通、验证玩法；B 无需服务器、代码不离本机、只支持 Python；C 功能最强但对零基础开发者门槛高。分档让每一阶段都有可验证成果。
- **后果**：
  - ✅ 起步快、风险可控；
  - ⚠️ MVP 判题不可靠（自欺风险），靠二期 Pyodide 解决；架构在 `domain/grading.ts` 留稳定接口，切换不影响上层。

### ADR-006：题库策略——AI 原创为主 + MIT 内容参考

- **背景**：题库来源是项目的核心问题之一，需确定获取方式。
- **备选方案**：
  - A. 用现成题库（力扣快照、doocs 题解）；
  - B. AI 批量原创生成；
  - C. 两者混合。
- **决定**：B 为主，MIT 许可题库仅作结构参考和补充。
- **理由**：产品以开源方式发布，版权必须干净。现成题库多是版权雷区；AI 原创无版权负担，且"双版本答案"正是现成题库都没有、AI 最擅长的——题库问题反而变成差异化。
- **后果**：
  - ✅ 版权干净、差异化；
  - ⚠️ AI 生成内容正确性需验证（见 ADR-007）。

### ADR-007：题库审核——Python 脚本自动验证 + 自愈，非人工

- **背景**：需确定实操题的审核方式（是否可用 Python 自动化）。
- **备选方案**：
  - A. 人工逐题审；
  - B. Python 脚本自动跑测试验证，不通过让 AI 重写（自愈循环）。
- **决定**：B。
- **理由**：找到 Meta 开源的 [synth_gen](https://github.com/facebookresearch/synth_gen)（MIT）正是这套思路——AI 生成题和答案后用语法检查 + 类型检查 + 跑单元测试三重验证，不通过让 AI 自己改，循环到通过。这是离线工具链，不违反"暂不做后端"。借鉴 [bosens-China](https://github.com/bosens-China/Python-100-Exercises) 的 `validate`/`check`（100 份参考实现通过 329 项检查，起始代码未被误判通过）和 [leet_study](https://github.com/wyw287/leet_study) 的"区分度检查"（注入烂代码验证测试够强）。
- **后果**：
  - ✅ 不用人工逐题审、质量有保障；
  - ⚠️ synth_gen 是训练大模型的重型工具，直接搬来太重——只精简借鉴"生成→跑测试→自愈"这一段，自己写轻量脚本。

- **落地进展（2026-11-28，v1.4.0）**：自动审核部分已实现为 `scripts/verify-questions.mjs`（零依赖、`npm run lint` 触发），含参考实现跑测试、起始代码防送分、烂代码防弱测试三层校验，并用系统 `python3` 复现 Pyodide 判题口径。"自愈"中的重新生成环节暂由人工驱动——接入模型 API 涉及付费决策（见 ADR-017 后的待办），当前为"人工生成 + 自动验证"的半自动形态。

### ADR-008：后端——暂不做，纯前端本地优先

- **背景**：需确定是否引入后端，以及数据持久化方案。
- **备选方案**：
  - A. 全套后端 + 数据库；
  - B. 暂不做后端，localStorage + JSON 题库。
- **决定**：B（项目确定暂不引入后端）。
- **理由**：起步阶段纯前端即可验证玩法，零运维成本，适合零基础 + AI 开发。进度存本地、判题在浏览器跑，都不需要服务器。
- **后果**：
  - ✅ 最快出成果、无服务器要管；
  - ⚠️ 换设备/清缓存会丢进度、无排行榜——已在文档中说明，靠仓储层抽象留门（见架构文档 14 节）。

### ADR-009：视觉——液态玻璃手写为主 + glasscn 参考，去 AI 味

- **背景**：视觉目标是"真正的现代液态玻璃毛玻璃风格"，同时要避免"AI 味"，需确定是否使用视觉库。
- **备选方案**：
  - A. 纯手写 CSS；
  - B. 手写为主 + 库点缀；
  - C. 视觉库为主。
- **决定**：B。核心玻璃质感手写（`backdrop-filter` + 半透明白边 + 柔和阴影），参考 [glasscn](https://github.com/TimMikeladze/glasscn)（MIT，13 套调色板、7 种材质、shadcn 风格源码）的设计变量。
- **理由**：真正的液态玻璃（Apple Liquid Glass 风格）核心全是 CSS，库不能替代审美；手写保证独一无二、最不"AI"。glasscn 与 shadcn 技术栈原生搭配，源码可控。备选还有 [lenscn](https://github.com/dushaobindoudou/lenscn/)（MIT，真实 SVG 折射，跨浏览器）。
- **后果**：
  - ✅ 高级、独特、可控；
  - ⚠️ 细节需打磨，费时间——用 glasscn 现成设计变量加速。

### ADR-010：视觉库——克制使用，全站最多 1 个效果件

- **背景**：候选技术栈包含 Magic UI / Aceternity UI，与"去 AI 味"目标存在张力。
- **备选方案**：整套引入 / 完全禁用 / 克制点缀。
- **决定**：克制点缀，全站最多 1 个效果件作点睛，其余保持克制；TanStack Query / dnd-kit / Recharts / react-resizable-panels 等当前不装。
- **理由**：找到 UIForge 的公开"品味地图"（[registry-map.md](https://github.com/TaewoooPark/UIForge/blob/main/skills/design-director/references/registry-map.md)）把组件库分两派——克制派（shadcn/ui、Origin UI、Park UI、tailark、Kibo UI、Motion-Primitives）与效果最大化派（Aceternity UI、Magic UI、reactbits）。原文评价效果派："一页放三个，你就得到了标准的 AI 造的样子"，规则是"每个项目最多一个效果件，只作点睛"。这为"是否使用视觉库"提供了明确判据。
- **后果**：
  - ✅ 兼顾漂亮交互与去 AI 味；
  - ⚠️ 需要审美判断力——用 04-UIUX 规范的具体标准来把关。

### ADR-011：书城——小册子内嵌 + 外部书籍导航卡片

- **背景**：书城需同时支持"小册子"和"外部书籍"，需确定呈现方式。
- **备选方案**：
  - A. 小册子和外部书都打包正文进产品；
  - B. 小册子内嵌网页阅读 + 外部书只做导航卡片跳原站。
- **决定**：B。
- **理由**：小册子自产、版权干净，可内嵌；外部书多为 CC BY-NC-SA 等许可，SA 条款有传染性会把产品许可绑死——只放链接卡片（书名/作者/简介/许可徽章）零风险、免维护更新。外部书免费开放（只是链接，不消耗金币）。
- **后果**：
  - ✅ 版权干净、维护成本低；
  - ⚠️ 外部书阅读体验依赖原站，不在产品内。

### ADR-012：版权合规——绿灯/黄灯/红灯分级

- **背景**：需厘清"不商用"场景下的版权边界，并建立合规清单。
- **备选方案**：随意用 / 分级管理。
- **决定**：分级管理：
  - 🟢 MIT / CC0 / CC BY（如 PyQuest、bosens-China、glasscn、synth_gen）→ 可用，署名即可；
  - 🟡 CC BY-SA / CC BY-NC-SA（如 handbook、ai-coding-guide）→ 只导航不复制正文；
  - 🔴 CC BY-NC-ND / 未标明 / 力扣快照 → 只放链接或不收。
- **理由**："不商用"只是部分许可的一个条件；CC 的 SA 条款会绑定衍生作品许可；力扣快照仓库明确写"仅供学习、不要他用"。开源 = 公开，风险比私下学习更大。
- **后果**：
  - ✅ 无版权尾巴，产品许可可干净地用 Apache-2.0；
  - ⚠️ 每引入外部内容都要核查许可——形成清单习惯。

### ADR-013：主题——跟随系统 + 手动覆盖

- **背景**：主题需同时支持浅色与深色，并跟随系统偏好。
- **备选方案**：只做深色 / 只做浅色 / 跟随系统 + 手动。
- **决定**：跟随系统（`prefers-color-scheme`）为默认，同时提供手动切换并记住选择。
- **理由**：跟随系统最省心、符合用户预期；手动覆盖满足个性化。bosens-China 已实现深浅色，可直接参考。
- **后果**：
  - ✅ 体验自然；
  - ⚠️ 两套主题下玻璃参数都要调到文字清晰（见 04-UIUX）。

### ADR-014：许可证——代码 Apache-2.0，第三方保留原许可

- **背景**：许可证方案确定为代码采用 Apache-2.0，第三方组件保留原有许可证。
- **备选方案**：MIT / Apache-2.0 / GPL 系。
- **决定**：代码 Apache-2.0；第三方依赖遵循各自许可；复制进仓库的组件（shadcn/glasscn）保留版权注释并列入 NOTICE。
- **理由**：Apache-2.0 有明确专利授权、企业认可度高，符合"当正式产品做"的定位；与现有 MIT 组件兼容。第三方许可由版权法自动成立，需在项目文档中写清楚。
- **后果**：
  - ✅ 专业、专利受保护、长期友好；
  - ⚠️ 需维护 NOTICE 文件；与 GPLv2 不兼容（当前无 GPL 代码，风险低）。不复制 GPL/LGPL/AGPL 源码（如 NekoACM 是 LGPL，只作独立服务思路参考）。

### ADR-015：平台——Web + PWA，不做原生 App

- **背景**：需确定产品形态（原生 App / Web 应用 / 桌面应用）。
- **备选方案**：原生 App / 桌面 App / Web / Web + PWA。
- **决定**：Web + PWA。
- **理由**：一套代码全平台可用、改完立即生效、零上架审核；PWA 可"添加到主屏幕"像 App 一样用，几乎零额外成本。原生 App 的体验和上架成本现阶段不值。
- **后果**：
  - ✅ 最快、最省、覆盖广；
  - ⚠️ 原生级性能/硬件能力有限——本项目不需要。
- **落地进展（2026-11-28，v1.4.0）**：PWA 已实现——手写 manifest + 自研 Service Worker（零依赖），预缓存应用外壳支持离线打开与添加到主屏幕。缓存策略：导航网络优先（离线回退首页）、静态资源缓存优先、约 13 MB 的 Pyodide 运行时明确不缓存以免占用手机空间（Python 实操题离线首次运行需联网一次，JS 实操题离线可用）。未采用 `vite-plugin-pwa`，理由与 ADR-009 一致：核心逻辑手写可控，不为几十行脚本引入构建插件。

### ADR-016：代码编辑器——CodeMirror（非 Monaco）

- **背景**：实操题需要网页代码编辑器。
- **备选方案**：
  - A. `@uiw/react-codemirror`（CodeMirror 6 的 React 封装，MIT）；
  - B. `@monaco-editor/react`（VS Code 同款，功能强但更重）。
- **决定**：A。
- **理由**：轻量，适合练习输入代码；与 bosens-China 的技术栈一致（它也用 CodeMirror）。Monaco 更重，对练习场景过剩。
- **后果**：
  - ✅ 轻、快、契合；
  - ⚠️ 高级 IDE 功能（如复杂补全）弱于 Monaco——练习场景不需要。

### ADR-017：第二语言——JavaScript 与多语言执行层

- **背景**：ADR-003 已定 Python 先行、第二语言优先考虑 JavaScript。需确定第二语言选型、判题方式与改造范围。
- **备选方案**：
  - A. JavaScript：浏览器原生执行，无需额外运行时；与开发栈 TypeScript 一致。
  - B. C 语言：需 WASM 移植或在线编译，链路复杂。
  - C. Java：需加载 JVM 的 WebAssembly 版本，资源重、加载慢。
- **决定**：选 A（JavaScript），本期范围为「多语言架构抽象 + JavaScript 首章」，版本号按 ADR 规则为功能更新（1.x.0），定为 1.1.0。
- **理由**：JavaScript 浏览器原生可跑，判题无需加载 13MB 的 Pyodide WASM，页面更轻、更符合无后端与秒开目标；且与 TypeScript 开发栈同源，维护成本低。C/Java 都要引入重量级运行时，与零基础、轻量定位冲突。范围上先打通架构并做一章验证，再决定是否大规模扩题，控制风险。
- **后果**：
  - ✅ 复用统一执行层，未来加第三语言只需登记 runner 与题库；JS 判题核心为纯函数，可在 Node 环境单测。
  - ⚠️ 执行层原按 Python 硬编码，本期已抽象为「语言 → runner」注册表并保留 Python 调用兼容；数据层升级为「语言 → 章节」两级，题库 id 需带语言前缀（py- / js-）；JS 的 `String()` 与 Python 的 `str()` 语义不同，出题时 expectedOutput 须按 JS 语义标定。
  - ⚠️ `new Function` 执行用户代码仍依赖 Worker 隔离与超时强杀防死循环；代码在本地运行、不离浏览器，与 ADR-008 无后端原则一致。

### ADR-018：检查更新——GitHub 公开 API（非自有后端）

- **背景**：设置页需提供「检查是否有新版本」能力，但项目无后端（ADR-008）。
- **备选方案**：A. 调 GitHub 公开 Releases API 查最新 tag；B. 自建版本接口（需后端，违反 ADR-008）；C. 只放一个跳 GitHub Releases 的链接，不自动判断。
- **决定**：A。C 作为兜底链接保留。
- **理由**：GitHub Releases API 公开可读、无需令牌、免费；版本号从 `package.json` 经 Vite 构建注入（单一真相源），与最新 Release 的 tag 做语义化比较即可判断。不引入后端，符合项目定位。
- **后果**：
  - ✅ 零成本实现，用户点一下就知道有没有新版；
  - ⚠️ GitHub 未认证 API 限流（60 次/小时/共享 IP），离线时不可用——已做四态 UI（检查中 / 已是最新 / 有新版 / 失败），失败时友好提示并保留跳转链接，不影响主流程。

## 3. 决策中的"三视角"留痕

对几个曾有争议的决策，保留当时的三视角分析，供日后复盘：

**关于"用现成题库 vs AI 原创"（ADR-006/012）**
- 全力反驳：现成题库版权是地雷，开源公开后风险更大，坚决不用力扣/CC BY-NC。
- 切换支持：起步可用 MIT 题库（bosens-China）快速填充跑通玩法。
- 中立对比：绿灯随便用、红灯坚决避开、中间地带 AI 生成补量——最稳组合。最终选 AI 原创为主。

**关于"视觉库用不用"（ADR-009/010）**
- 全力反驳：整套引入视觉库 = 组件展示厅，正是要避开的 AI 味。
- 切换支持：零基础 + AI 开发，视觉库能快速出漂亮效果。
- 中立对比：骨架手写保独特、视觉库最多点缀 1 个——既高级又高效。

**关于"基座选 PyQuest 还是从零 React"（ADR-004）**
- 全力反驳：原生三件套零依赖最快，PyQuest 已证明单文件能做出刷题产品。
- 切换支持：当产品做、状态多，React 自动管理省 bug，行业主流。
- 中立对比：原生适合验证玩法、React 适合做成产品；已过验证阶段，上 React。
