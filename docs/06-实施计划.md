## 1. 计划总览

### 1.1 为什么要分阶段

项目范围横跨界面、状态、领域逻辑、数据、题库、书城、判题、PWA。一次性全做，任何一个环节卡住都会导致整体无法运行，也无法定位问题。分阶段的唯一目的：**让每个阶段结束时都有一个能在浏览器里打开、能亲手点、能看到结果的东西**。

阶段划分与 PRD 的版本规划一一对应：

| 阶段 | 名称 | 结束时能做什么 | 对应 PRD |
|---|---|---|---|
| 阶段 0 | 环境与骨架 | 打开网页看到空壳界面，能构建、能部署 | 准备 |
| 阶段 1 | MVP 闭环 | 走完"引导→做题→看双答案→得金币→买内容→刷新不丢" | 第一期 |
| 阶段 2 | 质量与自动化 | 实操题自动判题、题库自动生产、成就打卡完整 | 第二期 |
| 阶段 3 | 规模化 | 第二语言、多语言判题评估、后端可行性评审 | 第三期 |

### 1.2 硬性执行原则

这五条来自协作约定，先写在最前面，后续所有任务都遵守：

1. **每步一个可验证成果**：一个任务完成后，必须能用一句话说清"现在能看到什么"，且能实际打开验证。
2. **单一最小版本**：一次只交付一个能运行的最小改动，不把多个功能揉在一次提交里。
3. **不可逆操作先确认**：删除文件、覆盖代码、推送远端、公开仓库、清除用户数据，执行前明确说明并征得同意。
4. **改动可追溯**：每次交付说明"改了哪些文件、为什么、怎么验证"；代码与文档同步更新。
5. **技术选型需批准**：文档未覆盖的新库、新方案，先给理由和取舍再采用。

### 1.3 里程碑（可运行检查点）

| # | 卡点 | 影响 | 处理方式 |

## 4. 依赖关系与关键路径

### 4.1 关键路径

以下链路是项目的最短完成路径，任一环延迟都会推迟里程碑：

```
T0.1 工程骨架
  → T0.5 领域/数据骨架
  → T1.3 题库数据
  → T1.6 判分函数 + T1.7 答题界面
  → T1.13 状态 Store
  → T1.19 引导 + T1.20 持久化
  → M2 闭环跑通
  → T2.1/T2.2 自动判题
  → M4
```

### 4.2 可并行的任务组

同一组内互不依赖，可并行推进，缩短总时长：

- 阶段 0：T0.2（样式）与 T0.5（层骨架）并行；
- 阶段 1 第 1 组（主题设置）与第 2 组（题库数据）并行；
- 阶段 1 第 5 组（书城）内部 T1.15/T1.17 可并行；
- 阶段 2：T2.6/T2.7/T2.8（成就/打卡/错题）相互独立。

### 4.3 跨阶段接口稳定性

为保证"换实现不动上层"，以下接口在阶段 0 定好后不再改签名（对应架构 14 扩展点）：

| 接口 | 一期实现 | 二期替换 | 上层是否受影响 |

## 5. 每步的交付与验证规范

### 5.1 单次交付必须包含的四段话

每个任务完成后，用固定格式汇报，便于审批和追溯：

1. **做了什么**：一句话说明本次目标；
2. **改了哪些文件**：列出路径与改动性质（新增/修改/删除）；
3. **为什么这样改**：涉及选型或取舍时给理由；
4. **怎么验证**：给出具体命令或操作步骤，以及"看到什么算成功"。

## 7. GitHub 推送流程（首个里程碑执行）

由于卡点 C2/C3，代码推送不能直接用 `git push`。采用以下流程，执行前需批准：

1. **确认凭证**：使用维护者重新生成的 token，或可直连的网络环境；
2. **对齐历史**：以远端 `73641ff`（单次"项目初始化"提交）为准，选择以下之一：
   - 方案 A（推荐）：本地以远端为基准重新同步，再在此基础上提交新代码；
   - 方案 B：本地压缩后的提交强制覆盖远端（会改写远端历史，需明确批准）；
3. **推送代码**：优先用 git push（若网络恢复）；否则用 GitHub API 通道（contents / Git Data API）逐文件上传；
4. **核验**：远端文件树与本地一致，提交信息正确。

> 该流程在 M0 或 M1 里程碑时执行一次，之后视网络环境决定是否常态化。
