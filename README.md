# 趣编（QuBian）

面向编程初学者的游戏化学习应用。每道题提供"专业版"与"大白话版"两套答案，用金币经济把做题、解锁、阅读串成闭环。纯前端、开源、不商用。

## 要解决的问题

现有编程学习材料有三个具体的缺口，趣编针对它们设计：

1. **对零基础不友好**：入门教材术语密集、缺少即时反馈，初学者容易在"看不懂"这一步放弃。
2. **解析只有单一深度**：主流刷题产品的答案面向已有基础的人，同一个知识点无法同时服务"看不懂"和"想深入"两类读者。
3. **缺少持续动机**：学习与奖励脱节，没有可累积的进度和回报，难以坚持。

## 核心设计

### 双版本答案

这是产品区别于同类工具的核心。每道题配两份解析：

- **专业版**：用规范术语讲原理，给出完整定义、边界条件和适用场景，面向有基础或想深入的读者。
- **大白话版**：用生活类比和逐行解释，假设读者零基础，面向初次接触该概念的人。

举例，"变量"这道题：专业版会说明它是"带类型的、可变的、指向内存地址的标识符"；大白话版会写成"一个贴了标签的盒子，你往里放东西，贴着同一个标签就能再找到它"。同一知识点，两种深度，由读者自行切换。

题库字段、写作标准和校验规则见 [05-题库数据规范](docs/05-题库数据规范.md)。

### 两种题型

| 题型 | 用途 | 判题方式 | 答案形式 |
|---|---|---|---|
| 选择题 | 测概念理解 | 前端比对选项，答完即显示解析 | 选项 + 正确答案 + 双版本解析 |
| 实操题 | 练写代码 | 起步为对照参考答案自评；中期由 Pyodide 在浏览器内跑测试自动判定 | 参考代码 + 逐行双版本讲解 |

两种题型都配双版本答案。操作题的自动判题在浏览器本地完成，代码不上传。

### 金币经济循环

做题与完成任务获得金币，金币用于解锁后续关卡或购买小册子，阅读小册子后返还部分金币，形成闭环。数值集中在一个配置文件里，可随时调整；以下是设计示例值，不是最终数值：

| 行为 | 金币变动（示例） |
|---|---|
| 答对选择题 | +5 |
| 完成实操题 | +10 |
| 解锁下一关 | −50 |
| 购买小册子 | −40 |
| 读完小册子 | +15 |

需要说明的设计缺口：当前循环以奖励和一次性消费为主，关卡通关、书籍读完之后缺乏长期消耗场景。这一点已记录在产品文档的风险项中，待玩法跑通后补充。

### 游戏化系统

每日任务、积分、等级、成就四套系统，数据均从做题与阅读行为派生，存于浏览器本地。它们与经济循环共用一套进度状态，避免多处维护。

### 书城

两条内容来源，版权处理方式不同：

- **我的小册子**：由自产的双版本答案按章节汇编，内嵌网页阅读器，用金币购买。内容为项目自有，采用 CC BY-SA 4.0。
- **外部书城**：书籍导航卡片，展示书名、作者、简介和许可信息，点击跳转原站。只做链接不复制正文，因此不涉及内容版权风险；免费开放，不消耗金币。

外部书籍只收录许可明确的内容，分级规则见产品文档与 [03-技术决策记录](docs/03-技术决策记录ADR.md)。

### 主题与平台

浅色与深色主题跟随系统偏好，并提供手动切换。应用形态为 Web / PWA，可"添加到主屏幕"离线使用。纯前端架构，无后端服务，学习进度存于浏览器本地——代价是换设备或清除缓存会丢进度，云同步与排行榜留待后续评估。

## 技术栈

| 层次 | 选择 | 理由摘要 |
|---|---|---|
| 框架与语言 | React + TypeScript + Vite | 生态成熟、AI 辅助开发出错率低、长期可维护 |
| 样式 | Tailwind CSS + shadcn/ui | 组件源码进入仓库、可控，不自带装饰性特效 |
| 图标与动效 | Lucide React / Motion | 动效只服务于交互反馈，不用于装饰 |
| 状态管理 | Zustand | 管理金币、进度、主题等全局状态 |
| 代码编辑器 | CodeMirror（@uiw/react-codemirror） | 比 Monaco 轻，适合练习场景 |
| 浏览器内判题 | Pyodide | Python 在浏览器运行，无需服务器，代码不离开用户设备 |
| 本地存储 | localStorage | 无后端阶段的进度持久化 |
| 部署 | GitHub Pages + PWA | 免费静态托管，无运维成本 |

每项选型的备选方案、取舍和后果记录在 [03-技术决策记录](docs/03-技术决策记录ADR.md)。视觉参数（液态玻璃的模糊值、透明度、描边、阴影，以及深浅两套色彩变量）固化在 [04-UI/UX 设计规范](docs/04-UIUX设计规范.md)。

## 代码结构（规划）

架构采用四层分层，依赖方向自上而下，领域逻辑不感知界面与存储细节：

```
src/
├── app/          # 应用入口、路由、全局 Providers
├── features/     # 按业务功能组织：onboarding / quiz / answer / economy / books / achievements
├── components/   # 通用 UI 组件与液态玻璃基础组件
├── domain/       # 领域逻辑：金币规则、解锁规则、判定逻辑（纯函数，可独立测试）
├── store/        # Zustand 状态定义与持久化
├── data/         # 题库、小册子内容与本地存储适配
└── lib/          # 工具函数、Pyodide 封装
```

设计约束写在 [02-架构设计](docs/02-架构设计.md)：单个文件不超过约定行数、跨层调用走明确接口、通用逻辑下沉到 `domain` 或 `lib`，以避免出现难以维护的超级大文件，同时不过度拆分。

## 路线图

阶段划分以可验证的交付物为准，每一阶段结束后都能实际运行和检查：

1. **第一期 · 可用闭环**：入门引导、选择题与双版本答案、金币结算、书城小册子、本地存储、深浅主题、PWA。目标是跑通"做题得金币 → 消费 → 再学习"的完整链路。
2. **第二期 · 质量与自动化**：Pyodide 自动判题、题库自动生成与验证工具链、成就与连续打卡、错题复习。目标是降低内容生产成本、提升练习有效性。
3. **第三期 · 扩展**：第二教学语言、多语言判题评估、按需评估是否引入后端（云同步、排行榜）。是否启动以实际需求和资源为准。
